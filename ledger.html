I asked an AI agent to buy six things. Here is where it broke.

Same agent, same task shape, six brands: find the price, pick a size or shade, add it to the cart. Every step was logged with what the agent saw and why it acted. Three passed cleanly, one passed after two dead ends, two never got to a cart. The interesting part is not the count. It is how close the ones that passed came to buying the wrong thing, and how the ones that failed were told why.

How this was run

Agent
Claude Fable 5 (claude-fable-5), operating through Claude Code. One action per step, reasoning written before each action and recorded verbatim.
What it read
The Chromium accessibility tree, pulled over CDP (Accessibility.getFullAXTree), filtered to rendered, non-hidden nodes. This is the same class of representation Playwright MCP and similar tool-driving agents consume. No screenshots were used to decide actions; they were captured after each step for this record.
How it acted
Playwright click, fill and selectOption on the node behind each tree reference. Headed Chromium 1223 (Playwright 1.60), persistent profile, 1280 by 860, US locale, New York timezone, no extensions.
Task
"Find the price of [product], choose [size or shade], and add it to the cart." One product per brand, chosen before the run. Runs started from the product URL where I had one, otherwise from the site's own search.
Supporting score
An open-readability audit of the product page, run after each trace on a clean load. 35 structured data, 35 operability, 15 headings, 15 images. Weights are mine and are explained below. The score is the footnote; the trace is the finding.
Date
All six runs and audits: 22 August 2026, between 15:58 and 16:15 US Eastern. Pages change; this is a snapshot.
  • Read-only past the cart. Nothing was purchased. No checkout was started. Items added to carts were left there.
  • No bypassing, one disclosed exception. When a site showed a bot check or refused a request, I retried once the way a person would (reload, or start from the homepage) and then stopped, with one exception disclosed in the verification record: on the 1 Sep re-run Amazon served a soft "Continue shopping" interstitial and the harness clicked it, an assist SSENSE never received. No CAPTCHA solving, no proxies, stock Chrome user agent. The browser was launched with Chromium's AutomationControlled feature disabled, a common Playwright setting that hides the navigator.webdriver signal. That is a partial disguise and it is disclosed here because it matters. To check that it did not shape the two blocked results, Nike and SSENSE were re-run on 27 August on a stock session (flag removed, fresh profile): same refusal modal on Nike's Add to Bag, same Turnstile wall on SSENSE. Both re-run traces are in the raw data. The session was not identified as an agent at the HTTP level; there is no settled standard for a person-directed browser agent to do so (Cloudflare's Web Bot Auth is the emerging one), and this run did not use it.
  • One run each. No cherry-picking across attempts. The Amazon run includes its dead ends and a harness restart because that is what happened.
  • What I could not see. Vision-based agents (Operator, Comet, Atlas and their kind use screenshots plus DOM and can see a highlighted size button or a Turnstile box that the tree omits, so tree-only findings are a lower bound for tool-driving agents, not a claim about all agents), merchant feeds, logged-in states, mobile layouts, and whatever these sites serve to agents they have partnered with. One run per brand, one afternoon, one model, one harness.
  • Amazon, knowingly. Amazon's robots.txt disallows ClaudeBot and Claude-User by name and its Conditions of Use restrict automated access. This run proceeded as an unidentified browser session: one item, read-only, nothing purchased. It stays in the record because it is the one site that refused and then did not, and because the tension between "no automated access" and "an agent shopping for a person" is the subject of this ledger, not a footnote to it.
  • Raw data is published. Every trace, every accessibility snapshot, every audit, every screenshot. Corrections log at the bottom.

Why it went the way it did

State you cannot trust

After selecting Brown, the tree reported two radios in the same group as checked: the outer "Dark Brown" wrapper and the inner "Brown". The visible label said Brown. I trusted the label. An agent that trusts the checked state ships Dark Brown.

Platform default

Shopify opens a product on its first available variant; on Boy Brow that is Dark Brown, and the page passes it into the cart with no confirmation. An agent told "buy Boy Brow" with no shade, or one that skips the picker, adds Dark Brown without anyone choosing it. The two-radios-both-checked state after selection is the real defect.

Control with no name

The purchase-frequency combobox in the cart drawer has no accessible name. It reads as combobox (unnamed) with options like "Ship every month".

The store asks agents not to do this

glossier.com/llms.txt says agents should prefer the Shop skill and UCP "over screen-scraping or scripting the storefront directly". The UCP discovery document is live at /.well-known/ucp. Shopify provides both.

Why it went the way it did

Refused at the till

Everything up to the cart call worked. The response was a modal: "We Couldn't Complete Your Request. Close this tab, disable any browser extensions (such as coupon or promo code tools), and reopen nike.com." The refusal was correct: an automated session was present. The stated cause was not: there were no extensions. The copy is written for the common case, and an agent relaying it would tell its user the same false thing. The bag stayed at 0. Price out of reach, sometimes

On the sale colorway the visible price spans are aria-hidden and the price exists in the tree only as a role-less generic node named by aria-label ("current price $91.97, original price $120"). Playwright's aria snapshot, the representation Playwright MCP feeds agents, drops it: what survives is "23% off" and "$16/month". On the full-price colorway "$120" is plain text. The JSON-LD carries 91.97, so a schema-reading agent is fine.

Out-of-stock dead end

The first PDP had every adult size disabled except M 12. Nothing in the tree says "try another colorway"; the agent had to infer it from the colorway links. It did.

Otherwise excellent

One h1, every control named, every image named, Product + Offer schema with a matching price. Readability 98. It did not matter.

It also means an agent told "buy the Charged Assert 10" that never touches the size picker adds whatever size the ranking chose, and the page never objects. The select does expose a "Select" option for the no-choice state; the search result skipped past it.

Control with no name, and barely a body

The size picker is a native select with no label, no aria-label, opacity 0.01, 62 by 27 pixels, sitting under a custom dropdown. The tree calls it combobox (unnamed). Playwright's selectOption timed out on it, a click timed out on it, the page re-navigated under me, and I had to restart the harness before a second selectOption went through.

Walled at the gate, once

The search URL returned the "Sorry! Something went wrong" page (the Dogs of Amazon). The homepage worked on retry, and the product page loaded. The wall is inconsistent, which is worse than consistent for anyone trying to build on it.

Noise

The results tree was 2,341 lines; the first two results were sponsored listings for a different shoe. The product page is 1,300+ lines, eleven h1s, 20 unnamed controls, seven image radios all named "Submit", and control names that contain raw "&#39;" entities.

Closed on purpose

No Product JSON-LD. No llms.txt. No UCP. robots.txt disallows about 100 crawlers by name including ClaudeBot, Claude-User, ChatGPT-User, Copilot, Devin and PerplexityBot; this run proceeded as an unidentified browser regardless, which is disclosed in the method. Readability 37, and the agent still got the right shoe in the cart. The page is operable; it is just not offered.

What the six traces actually say

Readability did not predict completion. The two highest scores in the set, Zara at 100 and Nike at 98, split: Zara passed in five actions, Nike was refused at the cart. The lowest score that reached a page, Amazon at 37, passed. What decided pass or fail was the gate (can the session get in) and the till (will the cart accept it), not the markup. That is a direct contradiction of the premise I started this project with, and it is the most useful thing in the ledger.

Where the page did matter is subtler and more dangerous. All four passes did pass, but every one of them had a point where a less careful agent would have put the wrong thing in the cart and nothing on the page would have objected: a size inherited from a search ranking, a shade inherited from a platform default, a size button that never says it is selected, two radios both claiming to be checked, a tap that commits without confirming. Those are not accessibility bugs in the compliance sense. They are places where the page lets a machine act on an assumption. When the machine is buying on your behalf, that is a governance problem, not a markup one.

The refusals were right; the reasons were not. Nike's modal named browser extensions that did not exist and not the automation that did. SSENSE's gate offered a checkbox the agent cannot see. Amazon's first page said something went wrong. None of those messages said "automated sessions are not allowed here", or pointed at the lane where identified agents are. A person relying on the agent gets a reason that is not the reason.

The feed layer is already live, and it is uneven. Both Shopify stores in the set publish an llms.txt and a UCP discovery document without anyone at the brand having to build them. Zara built its own UCP. Nike and Amazon publish neither, and Amazon disallows about a hundred agents by name in robots.txt. Whether a store is "agent-ready" in 2026 is increasingly decided by what platform it runs on, not by its product page.

About the supporting score

What it measures

Four things a tree-reading agent leans on, weighted toward the ones that let it decide and act. Structured data (35): a Product with an Offer carrying price, currency and availability, minus 10 if the schema price is not visible in the DOM. Operability (35): a named add-to-cart control, variant controls that all have names, price present as text. Headings (15): the first h1 in main names the product, no skipped levels, no navigation marked up as headings, minus 3 at three or more h1s. Images (15): no image in main without an alt attribute (alt="" is compliant), thumbnail controls named, minus 2 for junk alt text.

What it does not measure

Whether an agent can buy. Nike is the proof. It also does not count a single h1 as a rule (the HTML outline algorithm was removed from the spec in 2022 and WCAG has no such criterion), does not punish decorative alt="", and does not treat an unnamed carousel arrow the same as an unnamed size picker. It is a subset of what axe and the Rich Results Test check, reframed around the decide-and-act path. It is here so the traces have a "why" column, not as a product.

Known limits

  • One product per brand, one run, one afternoon.
  • The audit's accessible-name computation is an approximation of the accname spec, not a reference implementation.
  • Variant-control detection is heuristic and over-counts on pages with "you may also like" pickers (Glossier reports 263).
  • The audit was run on a clean load, scrolled once, with no drawers open. Earlier runs with a cart drawer open scored differently and were discarded.
